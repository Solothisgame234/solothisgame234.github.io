The orb that chased the ship

28 October 2026 · Solothisgame234

Players noticed a glowing dot that sometimes followed the ship around instead of being collected. It turned out to be simple math, and fixing it led to a second bug in how the game limits its frame rate.

Bug 1: an orb that never arrives

Every ship has a magnet: orbs within 130 units drift toward it. The original code moved each nearby orb a fraction of the remaining distance every frame, which is the standard "smooth follow" trick:

// old: close a fraction of the gap each frame
o.x += (ship.x - o.x) * k;
o.y += (ship.y - o.y) * k;

Here k grows with frame time, at a rate of about 9 per second. The trouble is that the target is moving. The ship flies forward at 430 units/s or more, so each frame the gap grows by the ship's movement and then shrinks by a fraction. Those two balance out when

gap ≈ ship speed / 9 ≈ 430 / 9 ≈ 48 units

An orb picks up when it's within 34 units of the ship's center. So an orb caught from behind settled 48 units back and stayed there, chasing the ship forever. At top speed (880 units/s) the gap was nearly 100 units, still inside the 130-unit magnet range, so it never let go either.

The fix: move with the ship, then close in

A caught orb now first moves by the same amount the ship moved this frame, and only then closes part of the remaining gap. Seen from the ship, the orb is no longer chasing a moving target. The gap only shrinks, and it shrinks quickly:

if (o.mag) {
  o.x += shipDx; o.y += shipDy;               // ride along with the ship
  o.x += (ship.x - o.x) * k;                  // then close part of the gap
  o.y += (ship.y - o.y) * k;
}
// collected when close enough, or 0.35 s after being caught at the latest

Two smaller changes came with it. Once an orb is caught it stays caught, so it can't drift out of range halfway in. And it's collected after 0.35 seconds at the latest, just in case. In testing, orbs caught behind, beside and above the ship were all collected in 0.07 to 0.10 seconds.

Bug 2: "60 FPS" that ran at 36

The same update added a frame rate setting: 30 FPS, 60 FPS or Unlimited. Lower and steadier often feels smoother than higher and uneven on weak phones. The browser calls the game once per screen refresh through requestAnimationFrame, so a cap has to skip some of those calls. The first version did the obvious thing:

// first try: skip the frame if less than 1/60 s has passed
if (now - last < 1000 / cap * 0.85) return;

On a 60 Hz screen that works. The test machine's screen was 72 Hz, though, and refreshes arrive every 13.9 ms. With a 60 FPS cap the threshold was 14.2 ms, so every second refresh was skipped and the game ran at 36 FPS. That's slower than asked for, and noticeably choppy. Screens at 75, 90 and 144 Hz each fail in their own way with this approach.

The fix: a schedule instead of a minimum gap

The cap now keeps a "next frame due" time that moves forward by exactly 1/60 s (or 1/30 s) each time it renders, and renders on whichever refresh lands closest to that time. To know what "closest" means, it keeps a running average of the screen's refresh interval:

vsync = vsync * 0.9 + (now - prevNow) * 0.1;      // measured refresh interval
if (now < due - vsync / 2) return;                 // not this refresh
due = now - due > interval ? now + interval        // after a stall, start over
                           : due + interval;       // otherwise keep the rhythm

Measured on a 144 Hz screen afterward: 30 FPS gave 30, 60 FPS gave 60.5, and Unlimited gave 144. The "start over" line stops the game from rendering a burst of frames to catch up after a pause.

Making the rest frame-rate proof

With the frame rate now up to the player, anything that happened "once per frame" became a bug. The light trail behind the ship stored one point per frame, so at 30 FPS it was twice as long and jagged, and at 144 FPS it was short. Thruster sparks were the same. Both now run on time instead: the trail records a point every 1/60 s during the physics steps, and sparks are emitted at 60 per second. The physics already ran in fixed 1/120 s steps, so movement and collisions were never affected.

Automatic 30 FPS for slow devices

Most players never open a settings menu. So during the first four seconds of real play on a new device, the game measures its frame rate. If it can't hold about 50 FPS, it switches to the steadier 30 FPS cap and shows a short note saying so. You can change it any time on the start screen or in the pause menu.

Takeaways

  • "Move a fraction of the way toward the target" only arrives if the target is still. For a moving target, work in the target's frame of reference.
  • A frame cap should be a schedule, not a minimum gap between frames.
  • If players can change the frame rate, anything counted "per frame" needs to become "per second".
